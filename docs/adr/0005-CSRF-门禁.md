# 0005 · CSRF 门禁：double-submit cookie 与按方法判定

**Status:** accepted (2026-10-26)

## Context

红线 #2（AGENTS.md §9.2）：鉴权不得依赖单一 `SameSite` 属性，所有 cookie 鉴权的写接口必须过 CSRF 门禁。v3 采用 Double Submit Cookie + 恒定时间比较，方向正确，但判定「是否需校验」时按「请求是否有 body」，放过无 body 的写请求（§10 记录的 bug）。§10 同时记录了一项义务：前端将来经 Nuxt server routes 代理请求后端时，代理调用非浏览器发起，须显式区分，不得依赖默认行为——该义务在本文件履行。

## Decision

1. **令牌下发**：会话签发（登录、刷新成功）同步下发 `nebula_csrf` cookie——随机 256 位十六进制、`Path=/`、`Secure`、`SameSite=Lax`、**非 HttpOnly**（SPA 需读取并经 `X-CSRF-Token` 头回显）。每次刷新轮转 csrf 值。
2. **门禁位置**：烧进 `AuthUser` 提取器——凡认证来源是 cookie 且请求方法为写方法（POST/PUT/PATCH/DELETE）的，必须 `X-CSRF-Token` 头与 cookie 值恒定时间相等。经 `AuthUser` 的未来写端点自动过门禁，遗漏在结构上不可能。判定只看请求方法，不看有无 body（v3 bug 的修正）。
3. **Bearer 豁免**：`Authorization: Bearer` 来源的认证跳过 CSRF——跨站页面无法携带自定义头，豁免成立。读方法（GET/HEAD/OPTIONS）豁免。
4. **cookie-only 写端点**（refresh，不经 `AuthUser`）通过独立的 `CsrfGuard` 提取器走同一比较逻辑。
5. **失败响应**：403 `csrf_invalid`；登出与刷新的 401/403 响应均附带清 cookie 头。
6. **SSR 边界预留**：将来前端经 Nuxt 代理调用后端时，后端无法区分跨站浏览器请求与 Nuxt 自身代理调用，届时须引入显式内部标记（如内部头 + 网络层隔离），不得让代理调用绕过本门禁的语义；实现时以新增 ADR 记录。

## Consequences

**得：** 门禁与认证提取器同生共死，新增写端点零成本合规；按方法判定消除 v3 的 body 误判类 bug；令牌随刷新轮转，被盗 csrf cookie 的有效期与 refresh 同步。

**失：** Double Submit 的理论弱点（攻击者可控子域可注入同名 cookie）被接受，与 v3 同级；SPA 必须实现回显（§3.3 的生成式 API client 将内建该行为）；恒定时间比较为自实现的异或折叠（长度先行的短路仅泄露长度，token 定长 64，可接受）。
