# 0007 · 用户数据所有权与级联删除

**Status:** accepted (2026-10-27)

## Context

`AccountRepo::delete_user` 手写枚举要删除的子表：验证码、refresh token、refresh 家族、用户。TOTP 与 OAuth 切片加入 `totp_recovery_codes`、`totp_login_challenges`、`oauth_authorization_codes` 后没有同步修改这里。连接池启用了 `foreign_keys=ON`，因此启用过 TOTP 或授权过第三方应用的用户在注销时最后一步 `DELETE FROM users` 会触发外键错误，返回 500；验证码已在删除前消费，用户重试还要重新收码。临时 SQLite 复刻确认：任一子表有行时删除失败，干净用户成功。

问题的根因不是漏了三条 DELETE，而是“哪些行属于用户”没有单一出处。每增加一张用户数据表，注销路径就多一次遗漏机会。

v4 尚未上线，没有需要保留的历史数据；迁移可以重建子表以补上外键动作。

## Decision

1. **所有权写进 schema。** 所有以 `user_id` 引用 `users` 的表一律使用 `REFERENCES users (id) ON DELETE CASCADE`；`refresh_tokens.family_id` 引用家族同样 `ON DELETE CASCADE`。覆盖 `refresh_token_families`、`email_verifications`、`totp_recovery_codes`、`totp_login_challenges`、`oauth_authorization_codes`（`refresh_tokens` 随家族级联）。
2. **注销退化为一条语句。** `AccountRepo::delete_user` 只执行 `DELETE FROM users WHERE id = ?`；级联由数据库在同一事务内完成，用户不存在时幂等成功。
3. **迁移重建子表。** 新增迁移在 `PRAGMA foreign_keys=OFF` 下重建上述表、复制既有数据、恢复索引与唯一约束，最后重新开启外键。SQLite 不支持直接给已存在的表追加 `ON DELETE` 动作。
4. **新增用户数据表必须遵守同一约定。** 以 `user_id` 外键接入 `ON DELETE CASCADE`；若将来出现需要保留的审计或法定留存数据，单独开 ADR 说明例外，不得靠修改注销 SQL 绕过。

## Consequences

**得：** 注销的完整性由数据库保证，未来新增用户数据表不会因为忘记改 handler 而失败；删除是单条语句，原子性由 SQLite 事务与外键共同承担；测试可以用一个“全副武装”的用户验证所有权不变量。

**失：** SQLite 需要重建子表，迁移比 `ALTER TABLE ADD COLUMN` 更重；审计/留存类数据不能直接复用该级联，必须显式设计例外；所有写入路径仍然依赖 `PRAGMA foreign_keys=ON`，连接配置是这一决策的前置条件。
