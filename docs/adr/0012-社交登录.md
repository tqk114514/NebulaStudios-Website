# 0012 · 社交登录（Google / Microsoft）

**Status:** accepted (2026-10-29)

## Context

AGENTS §0 把「Microsoft / Google 社交登录」列为保留（简化），ADR-0002 拍板了范围：仅已绑定账号可登录、未绑定的社交身份一律报错引导、不比对邮箱、不自动建号、绑定只在设置页主动发起。但 v4 尚未有任何实现：`src/` 里没有社交相关代码，`Cargo.toml` 连 HTTP 客户端依赖都没有（`reqwest` / `oauth2` / `openidconnect` 全缺），登录页的 Google/Microsoft 按钮指向不存在的 `/api/auth/{provider}` 路由（`app/pages/account/login.vue`），i18n 里也还没有对应文案。

v3（`Reference/`）的实现把社交身份编码为 `users` 表上的一组列（`google_id`/`google_name`/`google_avatar_url`/`microsoft_id`/`microsoft_name`/`microsoft_avatar_url`/`microsoft_avatar_hash`/`microsoft_avatar_sync`），并带一条完整的头像同步链与「登录时发现同邮箱账号 → 弹确认页 → 邮件验证绑定」流程。两者都是 v4 明确要砍的：头像改由信息页手动上传，绑定只允许设置页主动发起。

本文记录 v4 的实现约束与新增依赖；范围（保留什么、砍什么）仍以 ADR-0002 为准。

## Decision

1. **只取两项数据：provider 用户 id 与展示昵称。** provider id 是绑定的唯一凭据（`(provider, provider_user_id)` 唯一）；昵称仅供展示、可空、变化时随登录刷新。**不取头像、不取邮箱**——不取邮箱即不需要邮箱验证与「同邮箱自动绑定」那套（ADR-0002），也不需要在 Microsoft 侧验签 id_token 取 email。
2. **身份存独立表，不用 users 列。** 新增 `user_social_identities(id, user_id, provider, provider_user_id, display_name, created_at)`，`user_id` 以 `ON DELETE CASCADE` 引用 `users`（ADR-0007），`UNIQUE(provider, provider_user_id)`。一表一职责，避免 v3 那种「每加一个 provider 就加三列」的扩张，也让「一个用户可绑多个 provider」与「一个 provider 身份只能属于一个用户」由 schema 直接表达。
3. **Google 沿用 Cloudflare Worker 代理，服务端校验背书。** GFW 内无法直连 Google，故 Google 的 token 交换经 Worker；Worker 在转发 Google 响应时用 Ed25519 对 `timestamp + "\n" + <原始响应体>` 签名，服务端用配置的公钥验签（时间戳 ±300 秒 + 签名），再解析 Worker 已验签的 `id_token` 取 `sub` 与 `name`。签名链是 Google 身份的信任根，`/userinfo` 之类未签名数据不作为身份依据。Worker 的契约与 v3 一致（`Reference/google-oauth-proxy.js`），部署在仓库外。
4. **Microsoft 直连。** token 端点后经 Graph `GET /v1.0/me` 取 `id` 与 `displayName`。access token 经 TLS 且客户端带密钥认证获得，足以作为身份来源；不取 email，故不做 JWKS / id_token 验签。
5. **两者都强制 PKCE（S256）。** 授权请求携带 `code_challenge`/`code_challenge_method=S256`，`code_verifier` 与 `state` 落库（新增 `social_login_states` 表，单次消费 + 过期），不放进程内存——遵守红线 #4（OAuth state 不得只存进程内）。`plain` 不存在（红线 #9）。
6. **新增依赖。** `reqwest`（`default-features = false`，`rustls` + `json`；`rustls` 后端选 aws-lc-rs，与 `jsonwebtoken`/`lettre` 一致，规避 OpenSSL）用于出站 HTTP；`ed25519-dalek`（`pkcs8` + `pem`）用于 Worker 背书验签。版本经 crates.io 核定为 `reqwest 0.13.5`、`ed25519-dalek 3.0.0`（§1）。选 `reqwest` 而非 `oauth2`/`openidconnect`：Google 走 Worker 的取数路径与这两个 crate 的发现/JWKS 模型不匹配，手写两条取数路径更少而更直白。
7. **配置段 `social`**：`google_client_id`/`google_client_secret`/`google_proxy_url`/`google_proxy_access_client_id`/`google_proxy_access_client_secret`/`google_worker_signing_public_key`、`microsoft_client_id`/`microsoft_client_secret`、`base_url`（派生回跳地址 `{base_url}/api/auth/{provider}/callback`）。启动时校验：配了某 provider 的 client_id 才校验其必填项，全空则不启用社交登录。
8. **本轮只做后端。** config、迁移、领域/端口/存储、授权链（start + callback）、绑定/解绑端点与测试。前端登录页按钮接线与设置页绑定 UI 属后续切片。

## Consequences

**得：** 绑定关系由一张表与两个唯一约束表达，新增 provider 只加一个枚举变体与一个端口实现；身份来源收窄为 provider id，砍掉了头像同步、邮箱比对、自动建号、进程内待绑定态四处复杂度；OAuth 中转态入库，重启不丢、多请求不串。

**失：** 后端首次引入出站 HTTP 依赖（`reqwest` 及其 TLS 栈）与 Ed25519 验签（`ed25519-dalek`），依赖树与许可面扩大（`deny.toml` 需同步）；Google 通路依赖仓库外的 Worker 与一对签名密钥，密钥轮换与 Worker 可用性由部署侧负责；未绑定的首个用户无法自助绑定（设置页未落地之前，社交登录实际上不可用）。
