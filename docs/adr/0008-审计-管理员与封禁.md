# 0008 · 审计、配置化管理员与封禁

**Status:** accepted (2026-10-27)

## Context

AGENTS §0 把管理后台收敛为「统计 / 用户列表 / 封禁」，角色管理、客户端管理、白名单改由配置文件承担。v3 把角色放在数据库、审计写独立表，封禁只在登录时检查；v4 需要满足红线 #1 的会话撤销语义，并让封禁在**已签发的 access token 上立即生效**。当前 `FirstPartyUser` 只验证 JWT、不查库，封禁若只写数据库不会拦截已登录用户。

## Decision

1. **管理员角色由配置提供。** `NEBULA_ADMIN__EMAILS` 为逗号分隔邮箱列表，启动时规范化（trim + 小写）进内存；`AdminUser` 提取器在 `FirstPartyUser` 之后按邮箱判断，不落库。**邮箱必须已验证**才按配置获得管理员权限，避免未验证邮箱被抢注后直接取得管理面；角色变更需要重启，换来单一事实来源且不出现数据库角色与部署配置漂移。
2. **封禁是数据库状态，每用户至多一条。** `user_bans` 以 `user_id` 为主键；`kind` 只允许 `temporary` / `permanent`，`CHECK` 强制「temporary 必有到期时间、permanent 必无到期时间」。解封删除该行；封禁历史由审计表承担。
3. **封禁在认证接缝执行。** `FirstPartyUser` 解析 JWT 后查 `users LEFT JOIN user_bans`，用户不存在返回 401，封禁生效返回 403 `banned`；因此已签发的 access token 也无法继续调用第一方端点。封禁动作在同一事务内撤销该用户全部 refresh 家族，已签发的 OAuth access token 仍受 audience 隔离与短 TTL 约束。
4. **审计日志追加写、不随用户删除。** `audit_logs` 的 `actor_id` / `target_id` 存 UUID 文本、不建外键；`details` 存 JSON 文本。管理员封禁/解封必须写审计；审计列表仅管理员可读。清理任务不删除审计日志，留存策略待单独 ADR。
5. **Admin API 只做最小集。** `GET /api/admin/stats`、`GET /api/admin/users`、`POST/DELETE /api/admin/users/{id}/ban`、`GET /api/admin/audit`；角色、OAuth 客户端与邮箱白名单不提供管理端点，改配置文件。

## Consequences

**得：** 封禁对已签发会话立即生效；管理员身份只有一个来源；封禁与会话撤销在同一事务内完成；用户删除后审计仍可追溯；管理端点与第一方提取器共用同一封禁判定，不会各写一套。

**失：** 每个已认证请求多一次 SQLite 读；管理员列表变更需重启；`actor_id` 无外键意味着审计可能指向已删除用户（这是审计留存的有意取舍）；封禁历史只能从审计还原，`user_bans` 不保留历史。
