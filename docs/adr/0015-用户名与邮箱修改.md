# 0015 · 用户名与邮箱修改

**Status:** accepted (2026-11-16)

## Context

AGENTS §0 没有列出资料修改，但信息页文案明确用户可修改用户名、头像与邮箱。用户已有稳定 UID（`users.id`，UUID v7），修改登录标识不会破坏 refresh 家族、审计、社交绑定、同意记录等引用；需要决定的是修改路径、重新认证强度与用户名大小写语义。

## Decision

1. **UID 不随资料修改变化。** API 字段名保持 `id`，它是 UUID v7 的稳定用户标识；用户名与邮箱只是可变登录标识。前端不得用用户名或邮箱作主键。
2. **用户名大小写敏感。** `users.username` 去掉 `COLLATE NOCASE`；注册、登录、改名均精确匹配，`Alice` 与 `alice` 是两个不同账号。邮箱仍大小写不敏感。
3. **用户名修改要求当前口令。** `PATCH /api/user/username`，沿用 3–15 字符 ASCII 字母/数字/`_`/`-` 规则与精确唯一约束；成功后写 `user.username.change` 审计。UID 与现有会话不变。
4. **邮箱修改分两步。** `POST /api/user/email/change/request` 要求当前口令与新邮箱，向新邮箱发六位验证码；`POST /api/user/email/change/confirm` 验码后更新邮箱并置已验证，写 `user.email.change` 审计并向旧邮箱发安全通知。新邮箱同样过域名白名单与唯一约束。
5. **邮箱修改保留现有会话。** 不递增 `token_version`、不撤销 refresh 家族；用户明确选择以较小打扰换取体验，安全边界由“当前口令 + 新邮箱验证码”承担。
6. **待确认请求入库。** 新表 `email_change_requests`，每用户至多一条，含新邮箱、验证码哈希、尝试次数、过期时刻；重发重置验证码与尝试次数，60 秒冷却。过期行由清理任务删除。
7. **没有迁移。** 用户名 collation 变更与新增表都通过删除数据库文件后重启完成（AGENTS §9.3、ADR-0003 修订）。

## Consequences

**得：** UID 与所有关联不变；用户名大小写成为真实展示语义；邮箱变更证明了对新邮箱的控制，旧邮箱同时收到告警。

**失：** 现有数据库必须重建；`Alice`/`alice` 可共存，用户登录用户名时必须记住大小写；邮箱修改后旧会话仍有效，若会话已失窃，攻击者可在知道当前口令的前提下持续持有会话，后续需要评估是否改为全端下线。
