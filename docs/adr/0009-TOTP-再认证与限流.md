# 0009 · TOTP 再认证与端点限流

**Status:** accepted (2026-10-27)

## Context

v4 的 TOTP setup/enable 只要求第一方会话，不要求当前口令。被盗 access token 可以为未启用 TOTP 的账户生成 pending 密钥、用攻击者自己的验证码启用，并把恢复码一次性拿走；此后攻击者持有第二因子，用户被锁在账户外。TOTP 相关端点也没有独立限流：二段挑战虽有 5 次上限，但可反复签发；关闭 TOTP 的 6 位码没有尝试上限。改密虽然撤销 refresh 家族，却没有作废已签发的 TOTP 登录挑战，挑战在 5 分钟内仍可完成登录。

## Decision

1. **setup/enable 要求当前口令。** 两个端点都在修改 TOTP 状态前调用共享的 `verify_current_password`：口令错返回 401 `invalid_credentials`；用户缺失或哈希损坏返回 500。disable 与改密复用同一助手，避免三套口令校验各自漂移。
2. **TOTP 端点独立限流。** `/api/auth/login/totp`、`/api/user/totp/setup|enable|disable` 进入独立 GCRA 组（突发 10、每 2 秒补 1）；挑战自身的 5 次错误上限保留，作为第二层约束。
3. **改密作废未消费挑战。** `change_password` 在撤销 refresh 家族的同一路径调用 `invalidate_challenges`；改密前已签发的二段挑战不能在改密后继续完成登录。
4. **登录入口先查封禁。** 密码登录与 TOTP 二段都在签发会话前检查 `find_access_state`，封禁用户不能靠重新登录绕过 `FirstPartyUser` 的 403（ADR-0008）。
5. **不在本 ADR 处理 TOTP 密钥加密。** `users.totp_secret` 目前仍是明文列；密钥管理与轮换需要独立的配置/迁移设计，另行开 ADR。

## Consequences

**得：** 被盗会话不能单方面绑定攻击者验证器；TOTP 端点有独立的滥用预算；改密后旧挑战立即失效；登录与已认证请求共用同一封禁判定。

**失：** setup/enable 的请求体增加 `password` 字段，现有客户端必须同步升级；TOTP 测试必须覆盖错误口令路径；每 2 秒补 1 个令牌的限额在高延迟网络下可能误伤连续操作，参数需要部署观察后再调。
