# 0004 · API 响应契约：裸数据与统一错误信封

**Status:** accepted (2026-10-25)

## Context

v3 有两种成功形状（`RespondSuccess` 平铺键 / `RespondSuccessWithData` 包 `data`），`success` 布尔与 HTTP 状态码冗余为三个真相来源，限流特例靠新增响应函数生长，字段验证码与业务错误码混在同一命名空间（`Reference/internal/utils/response.go`）。前后端之间对「拿到响应先看什么」没有唯一规则。功能范围已由 ADR-0002 锁定，本契约在第一个业务端点落地前定死，避免形状随端点漂流。

## Decision

1. **成功（2xx）：响应体即数据本体**，不套信封；无内容可返回的动作用 `204` 空 body。成功类型与领域对象一一对应。
2. **失败（非 2xx）：全站唯一错误信封** `{"code": string, "message": string, "details"?: object}`（`src/error.rs` 的 `ErrorBody`）。`code` 机器可读、跨版本稳定，是前后端唯一契约；`message` 供日志排查，前端不得展示；`details` 携带结构化附加数据（如限流的 `retry_after`），随首个需要它的端点引入，不预建。
3. **HTTP 状态码表达粗分类**（§9.8 的指标、缓存与代理依赖它）；前端遇到未知 `code` 按 status 兜底通用文案，使前后端可独立部署。
4. **同一 `code` 恒配同一 status**：映射由 `ApiError` 变体在 `IntoResponse` 中一次性定义，handler 不得自选状态码。
5. **例外：OAuth2 Provider 端点**（authorize/token）面向第三方客户端，错误形状遵循 RFC 6749（`error` / `error_description`），不套本信封。
6. 否决备选：全信封 `{data}`/`{error}`（多一层嵌套，生成式 client 下无收益）；v3 修正版 `success` 标志（与状态码构成三重真相来源）。

## Consequences

**得：** 前后端各记一句话（2xx 即数据本体，非 2xx 即错误信封）；成功类型与领域对象一一映射，§3.3 的生成式 API client 直接生成；`details` 是唯一扩展位，形状不再生长特例。

**失：** 「这个端点成功时返回什么形状」依赖类型与文档回答（由生成式 client 兜住）；v3 前端的响应解析逻辑不可复用，需按新契约重写。
